# 代码研究

研究的目标是让读者能回答“它在业务中解决什么问题、入口在哪里、数据和控制如何流动、边界是什么、哪些内容仍未验证”。先保持原任务范围，再决定是否需要写报告。

## 运行模式

先判断模式，不要把预研自动变成新的交付物：

- **独立研究**：用户要求研究、分析、交接或研究文档。完成研究后，按用户指定的语言和格式回答；用户要求文件时才写入 `docs/research/`。
- **实现前预研**：用户正在请求实现、修复或重构，且目标区域未知。只做足以支撑实现的只读研究，然后回到原任务；不强制创建报告，也不扩大实现范围。
- **接手/warm-up**：用户要理解陌生代码库、准备交接或建立业务上下文。先用非研发语言说明模块在产品中的角色、谁触发它、用户/操作方和产品能看到什么、能力与边界，再用代码证据解释实现；没有直接用户界面时，说明操作方、外部系统或开发者可观察到的结果。

如果用户只问一个文件或一个符号的直接含义，优先简短解释；只有需要跨文件追踪、架构梳理或可复用文档时才进入完整研究流程。

## 研究边界与副作用

1. 记录主题、种子文件、明确的包含项和排除项。没有种子文件时先搜索入口、导出符号、路由或配置键。
2. 读取仓库的 `AGENTS.md`、`CLAUDE.md`、贡献指南和与目标直接相关的标准；把它们当作“文档证据”，不要当作源码事实。
3. 研究阶段不修改业务代码、配置、锁文件或生成物。实现前预研结束后才可回到原任务的写入阶段。
4. 写研究报告时只写用户要求的目标文件；可以创建 `docs/research/`，但先读取同主题报告并保护其中无关内容。不要运行会改写仓库的生成、迁移或格式化命令。
5. 记录研究时的仓库相对路径、`git` 基线（至少 commit；工作区有改动时注明），不要把机器相关的绝对路径或密钥写入报告。

## 发现文件与调用关系

从种子文件建立文件地图，不追求无边界的全仓库遍历：

1. **入口和下游**：导入、导出、类型、调用、继承、配置读取和本地依赖。
2. **上游和横向关系**：调用者、路由/事件注册、字符串注册、barrel export、同名实体、数据模型、schema、feature flag、版本约束、相关测试。
3. **运行时边界**：`package.json`、构建配置、环境变量、代码生成配置和外部包的公开契约。记录外部依赖的使用点，不阅读无关的第三方实现。
4. 文件地图说明每个文件做什么，以及关键入口或符号。调用关系由图或具体描述表达，无需额外分类列。大文件和生成文件只读与主题相关的符号、类型、配置和调用点。
5. 如果搜索得到多个同名入口或 Provider，列出候选并用导入方、注册点或用户给出的路径消歧；没有足够证据时停止扩展，标为 `[未验证]` 或请求澄清，不要把多个实现合并成一个。
6. 当连续一轮没有发现新的强相关文件，或达到合理的时间/token 预算时停止。报告已覆盖范围和有意省略的路径；不要为了超过任意文件数而中断用户，也不要自动扩展到弱相关模块。

优先使用项目可用的搜索和读取工具；工具名称因运行环境不同而变化时，用等价能力替代。只有平台提供并且文件组互相独立时才并行委派，主任务统一去重和核对结果。

## 阅读与证据

对每个核心文件阅读足以证明结论的实现、类型、分支和调用点；小文件可通读，大文件采用“结构扫描 → 相关符号深读”。测试用于确认预期行为，配置和文档用于确认约束，不能互相冒充。

每条重要结论使用仓库相对路径和行范围，例如 `packages/ui/src/Provider.tsx:24-93`。使用以下证据等级：

- **事实**：源码、测试或配置直接显示的行为，附对应引用。
- **文档事实**：项目文档明确写出的约束，引用文档路径和行范围。
- **[推断]**：由多个证据组合出的解释，明确列出依据，不写成事实。
- **[未验证]**：源码不可读、运行时才能确认或证据不足的内容；只描述缺口和下一步验证，不补写伪代码、具体返回值或用户体验。

不要把通用框架知识、命名直觉或“通常应该如此”写成项目事实。引用无法解析、行号不确定或只能依赖记忆时，降低结论等级或删除结论。

## 研究输出

独立研究需要文档时，参照 [report-template.md](references/report-template.md)，但按主题裁剪章节。报告至少说明：

- 研究主题、模式、范围、排除项、源码基线和证据限制；
- 如果是接手/warm-up：业务角色、参与者、主要能力、业务边界、用户或操作方可见的成功/失败结果，以及关键领域术语；这些内容必须区分事实和推断；
- 接手 Provider、入口或基础设施时，按下文“业务完整性”追踪直接业务使用方，区分共享运行时能力与实际业务操作；
- 产品型 warm-up 提供页面/入口/能力清单，覆盖范围内注册的列表页、详情页、表格和主要操作，附使用目标和证据；
- 文件地图、入口到效果的关键路径、数据/控制流和外部契约；
- warm-up 或存在三层以上跨文件调用链时，提供一张 Mermaid 或 ASCII 架构/调用链图；图中每个节点都必须能在文件地图或证据引用中定位。只有单文件直接解释时才可省略图；
- 已确认行为、边界条件、异常路径和副作用；
- 未验证问题与潜在风险，分别标注证据、影响、置信度和建议验证方式。

“产品角色”“用户/产品可见结果”“业务说明”和“领域术语”是接手/warm-up 主题的必需内容，且要先用非研发读者能理解的语言表达，再展开技术细节；对纯技术主题，使用“可观察行为、调用者和边界”。报告语言跟随用户或仓库约定，代码标识符保持原样。模板中的占位符、猜测性伪代码和没有证据的泛化风险必须删除。

### 接手研究的业务完整性

接手者需要知道“能做什么、什么时候不能做、操作后会看到什么”。入口列表只能建立地图，不能替代业务说明。

1. 从页面清单追踪范围内行为不同的业务使用方。Provider 研究也要覆盖这些使用方的主要动作，而非只验证包装关系。对每类页面记录“动作 → 条件 → 可见结果”，包括权限、资源状态、类型或版本造成的菜单隐藏、禁用和提示。
2. 将源码可确认的导航、弹窗、批量操作及加载、空、失败反馈写具体。沿直接调用点读取足够证据即可，不要求展开全部弹窗和后端。没有读取的反馈保留为具体缺口，运行时未测试不等于源码无法确认。
3. 先给简短页面地图，再按页面或流程展开操作明细。共享条件只解释一次，有差异的条件分别说明。摘要压缩表达，详细章节保留已经确认的动作和限制。
4. 预算不足时列出尚未覆盖的页面、动作及影响，不能把仍在范围内的核心业务分支改写成“由下游实现”便宣告完成。改写或更新已有报告时，逐项核对原有的动作、条件和结果，仍有效的内容都要保留。

### 所有报告的写作顺序与版式

所有报告都使用可扫描的编号章节，默认顺序如下：

1. `结论摘要`
2. `研究范围与文件地图`
3. `架构与调用路径`（单文件直接解释可省略）
4. `已确认行为`
5. `未验证项`
6. `术语表`（需要时保留）
7. `研究限制`

技术研究、实现前预研和增量更新也必须遵守这套公共版式。增量报告在末尾追加更新记录和 claim ledger。

接手/warm-up 报告在公共章节前增加产品导览，默认顺序如下：

1. `概述：它在产品中的角色`
2. `用户和产品能看到什么`
3. `页面与能力清单`
4. `主要操作与限制`（按页面或流程分组）

然后继续公共章节中的文件地图、调用链和实现边界。

用摘要帮助定位，用分节保留细节。各类报告都通过重组内容降低阅读密度，不把已确认的关键行为改成笼统概述。warm-up 先给产品地图，再进入代码细节。每段只表达一个主要判断，尽量用一到三句短句。并列内容使用列表或表格。调用关系使用 Mermaid 或 ASCII 图。避免用连续分号、长串括号或把多个结论塞进一段话。

读者背景用于决定解释深度，不写进报告的栏目名称。表头使用“含义”“职责”“使用条件”等内容名称。模板中的写作提示在成稿中删除。

为减少路径对正文的干扰，所有报告都在开头建立“证据索引”，为文件分配短标签。正文可写 `Provider:21-64`，索引必须把 `Provider` 映射到完整仓库相对路径。首次出现关键文件时可以同时写完整路径。证据索引不能省略行范围，也不能把标签当作无来源的装饰。

如果输出了报告文件，运行 `scripts/validate_report.py <report> --repo-root <new-repository>`。增量更新再加 `--previous-report <old-report> --previous-repo-root <old-repository>`，分别校验旧、新基线的引用、`report_id` 和 claim ledger。没有文件输出时，在回答中完成同样的人工检查，不要为了运行脚本创建文件。

报告身份使用稳定字段 `report_id = <seed>::<topic-slug>::<scope-slug>`，其中 `seed` 是仓库相对路径，主题和范围使用小写短横线规范化；范围描述研究问题和边界，不把首次发现的文件清单当作范围。发现相同身份的旧报告时：

1. 先读取旧报告和它记录的源码基线，建立旧结论清单。
2. 为每条重要业务、技术或不确定结论保留稳定 `claim_id`，用当前源码逐条复核，分类为 `未变化`、`已变化`、`已失效`、`新增` 或 `仍未验证`；不要只按文件 diff 推断业务结论。
3. 每条变化记录旧证据和新证据。旧路径/行号按旧 commit 校验，新路径/行号按新 commit 校验；文件删除或符号移动时保留旧引用作为历史证据，并补充替代路径或删除状态。
4. 只更新受影响的章节，保留仍有证据的既有业务上下文和技术结论；对失效结论保留简短记录并说明失效原因。
5. 在报告中追加更新日期、旧/新基线、范围变化、结论分类、claim ledger 和验证限制。

如果种子、主题意图或研究范围发生变化，创建新报告或明确版本化的报告，并链接相关旧报告；不要静默合并。研究边界内新发现的强相关文件不算范围变化。接手/warm-up 报告尤其要保留稳定的业务角色和术语，只有证据变化时才改写它们。

## 完成检查

研究结束前逐项确认：

- 入口、主要调用者/依赖和关键运行时边界已经覆盖，遗漏项已列出；
- 接手/warm-up 主题包含业务角色、能力、边界和可见结果，并且每项都有事实或推断依据；
- 接手 Provider、入口或基础设施时已经追踪至少一个直接业务使用方，或明确记录其不可访问和未验证原因；
- 产品型 warm-up 已提供页面/入口/能力清单，或明确记录页面注册信息不可访问；
- 产品型 warm-up 已逐项覆盖范围内的动作、条件和可见结果，既有报告中仍有效的业务细节没有因摘要或排版而丢失；
- 报告使用短摘要、清晰小标题、表格、列表和图示组织信息，关键结论没有埋在长段落中；
- 报告的正文引用使用已定义的证据短标签，完整路径集中在证据索引中；
- warm-up 的业务摘要不依赖研发术语才能读懂，产品型 warm-up 按产品地图到技术细节的顺序组织；
- warm-up 或三层以上跨文件链路有一张与文件证据对应的图；
- 每个重要事实或文档事实都有可定位引用，推断和未验证项没有伪装成事实；
- 报告没有秘密、绝对机器路径、未替换占位符或凭空生成的代码；
- 增量更新报告包含稳定身份、每条重要结论的 `claim_id`、旧/新基线和结论差异；旧/新引用按各自基线校验，范围变化没有被静默合并；
- 引用的文件存在、行范围仍有效，工作区只包含用户要求的报告改动；
- 输出回答了原问题。实现前预研还必须回到原实现任务，而不是停在研究报告上。
